SMS is a school management system I built for Prithvi Narayan Campus, B.Sc. CSIT. It's a Turborepo monorepo: a NestJS 11 API, a Next.js 15 web app, and shared packages for Zod schemas and config. This post covers the architectural decisions that mattered.

## Why event-driven?

A school platform does a lot of work that has nothing to do with the current request: sending enrollment emails, publishing scheduled announcements, notifying a batch about a new assignment. Doing that inline makes requests slow and fragile.

So the API treats these as events. The request handler writes to PostgreSQL, drops a job on a Redis-backed **BullMQ** queue, and returns. Workers pick up the job — email delivery, notification fan-out — with retries and backoff for free. Cron jobs handle scheduled announcements the same way: the scheduler enqueues, workers execute.

## One schema package to rule them all

The `packages/schemas` workspace holds shared Zod schemas, enums, and API response types. The NestJS API validates requests against them; the Next.js app infers its types from them. When a field changes, both apps fail to compile until they agree. In a monorepo this is the single highest-leverage pattern I know — the API and the frontend literally cannot drift apart.

## Auth: refresh/access token recycling

Access tokens are short-lived JWTs; refresh tokens rotate on every use. When a refresh token is redeemed, it's invalidated and a new pair is issued — a stolen refresh token dies the moment the real user refreshes. Combined with role-based guards (`ADMIN`, `TEACHER`, `STUDENT`), every route declares exactly who can touch it. Google OAuth rides on top for one-click campus logins.

## Real-time chat without melting the API

Chat runs on **Socket.IO** in its own gateway, authenticated with the same JWTs as REST. Messages persist through Prisma, and the gateway only fans out to rooms the user's role allows. Keeping the socket layer thin — auth, room membership, fan-out — and pushing everything else through the normal service layer kept it debuggable.

## Shipping it

The API ships as a Docker image to **AWS ECS**, with GitHub Actions handling build, test, image push, and deploy on every merge. S3 handles document and image storage. The boring pipeline is the point: deploys are a merge, not an evening.

## What I'd tell past me

Start with the queue from day one — retrofitting async work is painful. Put shared schemas in a package before writing the second endpoint. And write the CI/CD pipeline while the app is still small, when it's easy.
